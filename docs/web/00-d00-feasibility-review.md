### 0.1 本报告的输入边界（必须公开声明）

### 0.2 复核判据

一个设计提案"冻结可行"，当且仅当：

- 它能被现有接口**无损表达**，或缺失部分可收敛为**纯新增**代码；
- 不要求求解内核、协议语义、预算语义发生**跨版本破坏性变更**；
- 浏览器侧能在**不引入 Node polyfill 黑洞**的前提下完成校验与渲染；
- 任何"回放/追溯/DAG"承诺都能由公开 trace 的**实际字段**支撑，而不是由 UI 的想象力支撑。

## 1. 逐项只读核对

### 1.1 `user_agent.py` 入口与 `AgentRuntime` 预算准入

**事实（输入）**：入口为 `user_agent.py`；`AgentRuntime` 对 `max_method_loads` 施加 `0..1` 上限；原稿草案写 `2` 会被直接拒绝。

**推导结论**：

- 该上限的语义是**每次运行中同一"方法加载槽位"最多被占用 1 次**——即预算不是"计数累计"而是"去重准入"。UI 若把它当滑块或数字输入框（`min=0 max=N`）来呈现，必然产生超出 `0..1` 的合法视觉状态，用户一提交即被 host 拒绝。
- 因此 **`max_method_loads` 在 UI 上唯一正确的形态是布尔开关**（关 = 0，开 = 1），而不是数值控件。任何"预算进度条 / 剩余次数"都是对语义的误读。
- `⚠[待验证]`：拒绝是发生在 **RPC 层（manifest 参数校验）** 还是 **runtime 层（准入拒绝）**，决定了前端错误提示的措辞与可重试性。若在 RPC 层，是被 schema 直接挡下；若在 runtime 层，是运行中被拒。二者 UX 差异巨大。

**冻结影响**：若 G 的设计稿中存在 `max_method_loads` 数值输入或"预算剩余"指示器，**必须改动**，且改动是**纯前端**，无需触碰既有文件。

### 1.2 RPC manifest（`agent-host-v13.schema.json`）的方言属性

**事实（输入）**：存在名为 `agent-host-v13.schema.json` 的文件；原稿设想"直接把整个 manifest 交给浏览器 Ajv 校验 SolveResult"。

**为什么这是错的（结构性论证，非风格偏好）**：

1. **描述对象不同**。一个 host RPC manifest 描述的是**调用约定**：方法名、入参信封、出参信封、错误码、传输帧、版本协商字段。`SolveResult` 是**某一次方法调用的结果载荷**，通常是 manifest 中嵌套得很深的一个子 schema（例如 `$defs.SolveResult` 或 `properties.result`）。把 manifest 整体交给 Ajv 去 `compile()`，得到的校验器校验的是 **manifest 本身符不符合它自己的 meta-schema**，与你手上的 `SolveResult` 对象毫无关系——校验必然"通过"或抛出针对信封的无关错误，两种结果都是错的。
2. **方言可能不是 Ajv 默认方言**。Ajv 默认走 draft-07；若 manifest 标注 `2020-12`，需 `ajv/dist/2020`；若使用了 `unevaluatedProperties`、`prefixItems`、`$dynamicRef`，老方言实现会静默忽略或报未知关键字。`⚠[待验证]`：manifest 的实际 `$schema` 值与所用关键字集合。
3. **manifest 几乎必然包含 Ajv 不认识的宿主扩展关键字**（例如 `x-host-*`、`rpcMethod`、`budget`、`transport` 之类）。Ajv 默认对未知关键字不报错但也不生效；一旦开启 `strict: true`，则**整份 manifest 直接编译失败**。
4. **浏览器侧不应校验信封**。信封/帧/版本协商是已解析完成的信息，前端拿到的是**已解码的 payload**，前端只需要 payload 结构校验。

**正确做法（冻结建议）**：前端 **不校验 manifest**。前端校验对象是**从 manifest 中抽取出的 `SolveResult` 子 schema**（构建期抽取，不运行期抽取）。这要求：

- manifest 中 `SolveResult` 是**可被稳定抽取的具名节点**（`$defs` 下具名，或 `$id` 可寻址）；
- `⚠[待验证]`：若 `SolveResult` 只是内联匿名 schema，则"构建期抽取"会退化为脆弱的正则/路径硬编码 → 升级为 §6 阻塞项。

### 1.3 `packages/protocol` 导出链中的 `node:crypto` 与浏览器隔离

**事实（输入）**：`packages/protocol` 的导出链引入了 `node:crypto`。

**后果（必然，非推理）**：

- 浏览器打包器（Vite/esbuild/webpack 5）在解析 `node:crypto` 时**要么报解析失败，要么替换为空 stub**（通过 `resolve.fallback`），后者更危险——它会让哈希/签名函数在运行时抛出 `crypto is not defined` 或返回错误结果，且**只在特定代码路径触发**，造成难以复现的线上缺陷。
- `node:crypto` 通常出现在**摘要/校验和/签名/ID 生成**路径上。这意味着：**protocol 的"身份"与"完整性"语义与 Node crypto 深度耦合**。

**浏览器隔离需求（结论）**：

- 必须引入 **web 侧 crypto 适配层**（`crypto.subtle` / `WebCrypto`），并让 `packages/protocol` 通过**条件导出或注入式接口**选择实现，而不是让打包器做 fallback stub。后者是"假装能跑"，会在冻结后被下游复现为 P0。
- 隔离边界应是：**浏览器只消费已计算好的摘要/ID**，或**在浏览器内用 WebCrypto 独立计算**——不能静默降级为"用 Node 结果或 stub 结果"。
- `⚠[待验证]`：`node:crypto` 是**顶层静态 import** 还是**函数内动态 import**。顶层静态 import 会让整个 protocol 包在浏览器侧不可用（除非深度改动既有文件，进入白名单）；动态/延迟 import 则可在 web 侧仅避开该路径，改动面显著更小。这一条**直接决定白名单条目**（§5）。

### 1.4 `SessionLog` 与公开 trace 的结构差异

**事实（输入）**：公开 trace 的字段集为 **`seq / kind / id / state / code`**；`SessionLog` 是更完整的内侧记录。

**差异清单（关键）**：

| 维度 | SessionLog（内侧） | 公开 trace | 前端后果 |
|---|---|---|---|
| 顺序 | 有 | `seq` ✅ | 可排序 |
| 事件类型 | 丰富 | `kind` ✅ | 可分类 |
| 对象标识 | 有 | `id` ✅ | 但 `id` 语义**未定义为节点/边** |
| 状态 | 有 | `state` ✅ | 可渲染状态机 |
| 错误/原因 | 有 | `code` ✅ | 仅码，无消息与栈 |
| 依赖关系（DAG 边） | 有 | ❌ 缺失 | **无法还原 DAG** |
| 推导/因果链 | 有 | ❌ 缺失 | **无法展示"为什么"** |
| 时间戳 | 有 | ❌ 缺失 | **无法做时间轴、耗时、并发** |

**结论**：前端能做的**上限是 L1 摘要回放**：

- L1（可做）：按 `seq` 排序的事件流；按 `kind` 分组；按 `state` 着色；按 `code` 归因到已登记错误码。
- L2（依赖图，**当前不可实现**）：没有边，任何 DAG 渲染都是**伪造**。
- L3（时间轴/耗时/因果动画，**当前不可实现**）：没有时间戳与推导关系。

任何"完整回放"文案必须**降级为"摘要回放"**，并显式向用户说明缺失维度。

### 1.5 进程生命周期与取消机制

**事实（输入）**：存在 `session.stop`；原稿把 `session.stop` 直接等同于"用户取消"。

**为什么这两者不等同**：

1. `stop` 的语义是**停止会话**（关闭通道、停止接单），通常在协议层实现为"不再接受新任务 / 关闭流"。它**不保证**当前正在执行的求解被中断。
2. 求解往往是**外部子进程**（Python worker / solver binary）。会话通道关闭**不会**向子进程投递信号，子进程会**继续跑完**（"孤儿进程"），占用 CPU/内存/许可证槽位，在某些求解器上还会**占用本地锁文件**，导致下一次启动直接失败。
3. 因此"用户取消"需要三件事同时成立，缺一不可：
   - **显式取消令牌（cancel token）** 从 UI → host → worker 全程贯穿；
   - **worker 侧的中断点**：求解循环必须响应中断信号，而不是只在结束后检查；
   - **孤儿清理**：会话关闭后，host 必须对**未正常退出的子进程**做 kill/wait，并将清理结果作为**可观测事件**回报。

**前端结论**：

- UI 上"停止"与"取消"必须是**两个不同动作**，或至少是**两级确认**：停止 = 停止接收，取消 = 停止 + 中断 + 清理。
- 若 host 未提供取消令牌透传，则前端**不能宣称"取消"**，只能宣称"断开"——这是**能力缺失**，必须标注。
- `⚠[待验证]`：`session.stop` 的 RPC 定义中是否存在 `cancel` 参数 / 是否存在独立的 `session.cancel` 方法 / host 是否有对子进程的 SIGTERM→SIGKILL 阶梯。这直接决定 UI 文案能否写"取消"。

### 1.6 新建目录是否会被既有构建链误包含

**风险面 1：`tsc -b`（solution-style project references）**

- `tsc -b` **只构建根 tsconfig 的 `references` 中列出的项目**，不做目录扫描。因此默认情况下 `apps/web-demo` 与 `packages/web-contract` **不会被包含**，是安全的。
- **但**：若根 tsconfig 使用了 `include: ["**/*"]` / `files` 通配，或 `tsconfig.base.json` 被某个 glob 引用，则新目录会被吸入并**继承旧的严格度与 target**，产生大量与新包无关的编译错误。`⚠[待验证]`：根 tsconfig 的 `include`/`references`/`files` 实际写法。
- **判定**：只要坚持"新目录各自有独立 tsconfig，且**不加入**根 references"，即为**零侵入**。

**风险面 2：`packages/protocol` 的条件导出**

- 若改动 `exports` map，**任何**既有消费者（含 Node CLI）都会受影响。这是 §5 白名单中**风险最高**的一条，必须保证 `node`/`default` 分支语义不变。

**风险面 3：Python 打包规则**

- 若使用 `setuptools.find_packages()` 且 `where` 指向仓库根，新增的 `python/astra_web` **可能被扫入**；若使用显式 `packages=[...]` 列表，则不会被扫入。
- 若使用 `hatchling` / `poetry` 的 `include`/`packages` 配置，同样取决于是否显式列举。
- `⚠[待验证]`：打包后端与包发现方式。**这是最容易"静默带上"的一项**。

## 3. 五大陷阱深度复核

### 3.1 `max_method_loads = 2` 会被拒绝

- **性质**：必然成立的拒绝，不是概率问题。
- **根因**：该字段语义为**去重准入位（0 或 1）**，不是累加计数。
- **冻结判定**：任何以数值输入、步进器、区间滑块、"剩余预算"形式呈现此字段的设计，**判为不可冻结**。
- **正确形态**：布尔开关 + 明确的帮助文本说明"开启即允许一次方法加载槽位占用"。
- **下游风险**：若 UI 隐藏该字段而使用默认值，必须显式确认默认值落在 `{0, 1}` 内。

### 3.2 直接用 Ajv 校验整个 manifest

- **性质**：方法论错误，两种失败模式（假通过 / 编译失败）都不可接受。
- **根因**：描述对象错配（信封 schema vs 结果载荷）+ 方言错配 + 未知关键字错配。
- **冻结判定**：凡出现 `ajv.compile(manifest)` 或"用 manifest 校验 SolveResult"表述的方案，**判为不可冻结**。
- **正确形态**：构建期从 manifest 抽取 `SolveResult` 子 schema → 独立 Ajv 实例（匹配 `$schema` 方言，2020-12 用 `ajv/dist/2020`）→ 关闭 strict 未知关键字报错（或先清洗扩展关键字）。
- **前置依赖**：`SolveResult` 必须是 manifest 中**具名/可寻址节点**（见 §1.2 ⚠）。

### 3.3 "任意结果完整回放"

- **性质**：能力缺失，必须降级为 **L1 摘要回放**。
- **根因**：公开 trace 无时间戳、无依赖、无推导，无法支撑"完整"二字。
- **冻结判定**：任何 UI 文案、按钮、菜单项出现"完整回放 / 全量回放 / 时间线回放"，**判为不可冻结**。
- **正确形态**：文案统一为"摘要回放"，并在 UI 中以**显式占位**说明"依赖关系与时间信息不可用"——把缺失呈现出来，而不是让用户以为是 bug。

### 3.4 从 trace `id` 猜测 DAG 边或义务覆盖

- **性质**：**无据推断**，会产生看似合理但错误的知识图谱，是最危险的一类缺陷（静默错误）。
- **根因**：`id` 仅是标识，未在公开契约中定义父子/先后/覆盖语义。`seq` 顺序 ≠ 依赖顺序（事件序列可以是并发的线性化编码）。
- **冻结判定**：任何"根据 id 前缀 / 层级 / 出现顺序连接节点"的实现，**判为不可冻结**，无论命名多直观。
- **正确形态**：
  - 只呈现**扁平事件流**；
  - 若必须呈现"关联"，只能呈现**同 `id` 聚合**（同一对象的多次状态变更），且明确标注"关联，非依赖"；
  - 义务覆盖视图**直接禁止**，直至 host 侧新增显式覆盖字段。

### 3.5 `session.stop` 等同于用户取消

- **性质**：语义混淆 → 必然产生孤儿进程/资源泄漏 → 长期稳定性问题。
- **根因**：`stop` 是通道生命周期操作，取消是任务生命周期操作。
- **冻结判定**：把 `session.stop` 直接绑定到"取消"按钮语义的，**判为不可冻结**。
- **正确形态**：
  1. UI 区分 **断开** 与 **取消**；
  2. 取消需要**取消令牌透传**（UI→host→worker）+ **worker 中断点** + **孤儿清理与回报**；
  3. 若第 2 项中任一环缺失，UI 只能提供"断开"，且必须提示"底层计算可能仍在继续"。
- **前置依赖**：`session.stop` RPC 定义是否含取消语义（§1.5 ⚠）。

## 5. 最小变更白名单（建议改动的既有文件及改动范围）

> 原则：**能不动就不动**；每一项都给出"改动范围上限"，越界即需重新冻结评审。

| # | 文件 | 改动范围（上限） | 触发条件 | 风险 |
|---|---|---|---|---|

| W2 | `packages/protocol` 中承载 `node:crypto` 的**单一文件** | 仅将其拆为 `crypto.node.ts` / `crypto.web.ts` 双实现 + 一个转发入口 | 同 W1 | **中** |

## 8. 结论

**总体判定：可进入冻结，但须以 §7 中 P0 级（G1–G5）设计改写为前提，并以 §4 的 T1/T3/T5/T8 四项试验结果作为最终闸门。**

- 前端方案在**事件流展示层**与**会话启动/断开**路径上，与当前基线**结构兼容**，且大部分能力可通过**纯新增包**（`packages/web-contract`、`apps/web-demo`）实现，对既有代码侵入面小。
- 三处**硬缺口**必须在冻结文本中显式承认：**取消语义（B1）**、**深度回放（B4）**、**浏览器 crypto 隔离（B3）**。把缺口写进设计，比让 UI 假装拥有它更安全。
- 本报告所有 `⚠[待验证]` 项在 T1–T10 完成后应回归更新；`⚠` 项若与结论冲突，**以试验为准**。
