## 5. 多路径候选池：R2 是“单链审计”，不是“独立 8 路票池”

需要区分三个概念：独立答案票池、锚定审计链、路线级多路径。

### 5.1 答案级审计链：活跃，但不是独立候选池

98 个候选全部固定经历 8 次 `CONSENSUS`，但**这是 R2 时的旧实现**，不是当前 5-independent ballot 实现。

R2 运行时间 10:48–11:30，早于 `077f608`（14:44，`feat(consensus): independent ballots instead of self-confirmation`）。旧代码的关键条件是：

```text
isBlind = round === 0 && maxConsensus >= 2
```

所以 `maxConsensus=8` 在 R2 中实际是：

```text
1 个 seed WorkPacket 候选
+ 1 次独立盲解（round 0）
+ 6 次锚定对抗审计（round 1–6，审计上一轮候选）
+ 1 次证书自检（round 7）
= 每题的独立样本只有 seed + 1 次盲解
```

实际 trace 只把 8 次统一标成 `CONSENSUS`，没有导出每轮子阶段；调用总数与旧实现吻合：**98 × 8 = 784**。

这说明：

- **8 轮调用和 6 次反复审计是真实的**；
- 但 6 次审计大多锚定上一轮自己的答案，存在**自我确认（self-confirmation）**；
- 不能用 `98 × 8` 直接宣称“8 个独立样本”；
- 真正的 `5 独立 + 2 审计 + 1 证书` 是 R2 之后才改的，尚无 100 题复跑证据。

### 5.2 路线级多路径：没有证据

文档 §5.3 的 G2 要求：

- `NEW_ROUTE` 提案；
- 机制签名不同；
- 绑定未决义务；
- 独立 `routeId`；
- 跨路线前提隔离。

本轮 trace 没有：

- `NEW_ROUTE` 事件；
- 第二路线产物；
- route admission / dependency admission 的可观测计数。

`metrics.routed=12` **不是 G2**。根据 `python/astra_bridge/agent_runtime.py`：

```python
if kind == "REPAIR" and data.get("kind") == "TOOL_ROUTE":
    routed += 1
```

这里的 `routed` 是 `REPAIR` 阶段的工具路由，和动态第二路线无关。12 次全部同时 `forced=12`、`obeyed=12`，更像强制工具轮，而不是 G2。

结论：

> **R2 有“1 个 seed + 1 个独立重解 + 6 次锚定审计”的单链候选生成/审计；没有真正的 8 路独立票池，也没有可证明的路线级多路径候选池。**

## 6. 反复评审机制：有“6 次锚定审计”，没有“R2→REPAIR→R4 反复修复”

### 6.1 R2 评审活跃，但只有一轮

| 指标 | 结果 |
|---|---:|
| 有候选的题 | 98 |
| `review_calls = 1` | **98** |
| `review_calls = 0` | 2（FIELD_VALUE） |
| `R2` trace | **98** |
| `front_spent = 1` | **98** |

每个候选恰好一次 R2，第二道 review 预算没有被使用。`front_spent` 也确认：前段只发生了 R2，没有 R0/R4。

### 6.2 REPAIR / R4 为 0

- REPAIR 事件：**0**
- R4 修复复核：**0**
- 修复阶段模型调用：**0**
- 本轮 profile 实际配置了 `max_repairs=2`，但 REPAIR 事件仍为 0
- R2 summary 没有导出 challenge 明细，无法区分“R2 没提出有效 Challenge”与“challenge 被后续门禁丢弃”

因此：

- 文档 §6.3 的“R2 提出 Challenge → REPAIR → R4 原子替换/回退”在本轮**没有被执行**；
- 不能从本轮结果推断 REPAIR/R4 的通过率、回退率或修复增益；
- 只能说它们在代码/测试中存在，不能说是 100 题实跑验证过的能力。

### 6.3 闭合检查有发现，但没有修复证据

- `closure_evaluations=98`
- `closure_defects=5`（5 题各 1 次缺陷）
- 这 5 题最终仍交付候选，且 stopReason 都是 `REVIEWS_COMPLETE`
- 没有 REPAIR 轨迹

所以这 5 次闭合缺陷：

- 可能被同题后续 WORK/CLOSURE 轮吸收；
- 也可能只是被记录后继续交付；
- 当前 summary **不足以证明缺陷已被修复**。

### 6.4 真正的“反复”发生在 consensus，不在 M4

R2 当时的真实重复结构是：

```text
1 次独立重解 + 6 次锚定对抗审计 + 1 次证书自检
```

这属于**答案级反复审计**，但不是独立多候选池，也不是 M4 的多次候选推导评审。把两者混写成“反复评审机制”会同时高估独立性和 M4 的实际使用程度。

`077f608` 之后当前代码才变成：

```text
5 次独立重解 + 2 次对抗审计 + 1 次证书自检
```

但该实现尚未在 100 题全量记录中复跑。

### 12.3 真正的根因链

不是单点 bug，而是四层连续偏移：

1. **定义偏移：把锚定审计算成独立票。**
   `maxConsensus=8` 的数字很好看，但从 10-19 到 10-27 之前，独立重解只有 1 个；连同 seed，最多也只有 2 个相对独立的候选。8 轮投票中的 6 轮在审计上一轮答案，容易把同一个错误反复确认。

2. **KPI 偏移：候选率替代正确率。**
   稳定性确实是必要条件，但 HANDOFF §0 写的是“只以正确率判断优劣”，§9 的执行目标却变成“先 100/100 候选”。没有把“达到 88/100 正确、92% 三次全对”设为不可跳过的门禁，导致候选率成为事实上的终点。

3. **范围偏移：工具数量替代能力收益。**
   26 个算子、82 个行为、WASI、R0/G2/REPAIR 都是真实工程量；但 10-24 已经知道 26 个算子在目标 100 题上只命中 24 题，新增 9 个命中 0 题、预计正确率贡献 0。继续扩面是用“架构完整度”替代“题目正确率”。

4. **证据偏移：合并/定向结果替代盲跑结果。**
   10-20 的 100/100、91/8/1，10-26 的并集 98/100、10-27 的两段合并 98/100，都包含了定向修复或重跑。HANDOFF 已明确说这些不能当盲跑成绩，但顶部状态和架构文档仍容易被读成“系统已经达到 98/100 正确”。

### 12.4 为什么说 10-27 不是起点

10-27 的 `077f608` 修复的是 consensus 的独立性问题，但它发生在 R2 100 题跑完之后：

当前代码的：


**没有对应的 100 题全量复跑记录**。因此：

- 10-27 是纠偏动作；
- 10-19 是 consensus 设计起点；
- 10-21 是把“候选优先”制度化的时间点；
- 10-25 是把“E2E 完成”写成“能力完成”的叙事分水岭。
